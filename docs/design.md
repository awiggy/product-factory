# 设计说明

## 目标

让一个 AI 产品从想法到上线的过程可重复、可追踪、可中断后继续，同时把“AI 自作主张”的风险压在少数几个人工审批点上。

## 核心取舍

1. **流程由代码控制，AI 只在阶段内部自主。** 阶段顺序、闸门、审批写在 `stages.json` 和 `factory_gate.py` 里，不靠一个大 Agent 在对话中决定下一步。固定的编排写进代码更稳，也便于中断后继续（与课程 s16 工作流运行时的思路一致）。
2. **一个机器可读的状态文件，其余是给人看的 Markdown。** `factory/state.json` 只记录阶段、证据、审批、豁免和历史；内容放在各阶段文档里。没有为每份文档设计 JSON schema，避免维护负担；需要结构化的地方（评测用例）才用 JSONL。
3. **证据分级，不允许以低冒高。** mock 通过、真实冒烟通过、线上验证通过是不同的事。闸门按阶段要求最低等级；条件不具备时只能由用户豁免，豁免会留痕。
4. **审批记录原话。** 签字必须附用户原话，审批随产品版本失效（v2 需要重新签 PRD）。
5. **默认方案与沿用现状并存。** 新项目直接采用默认技术栈，避免每次开放式选型；已有项目沿用合理技术栈，不为模板重构。
6. **部署不默认任何厂商，也不默认危险捷径。** 平台差异放进适配器；课程里的火山引擎经验保留为适配器，但数据持久化、权限、密钥处理按更严格的规则修订。
7. **每个 Skill 仍可独立使用。** 阶段 Skill 只引用自己目录内的文件；product-factory 是可选的总入口，不是依赖。

## 为什么增加了一个总入口

原 `agent-product-delivery-skills` 刻意不设总控 Skill，各阶段不自动衔接。对单次任务这是对的，但工厂需要回答“现在在哪、能不能往下走”。这里的折中是：总入口只负责状态与闸门，不做阶段内的工作；阶段之间的推进仍然需要闸门通过，关键节点需要用户签字。

## 状态机

```text
not_started → in_progress ⇄ blocked
                  │
                  ├─(闸门通过 + advance)→ passed
                  └─(可跳过阶段 + 理由)→ skipped
operate ──iterate──▶ 归档 history/vN，版本 +1，回到 prd（变更模式）
```

写入是原子的（临时文件 + 替换），中断不会留下半个 state.json。

## 权限档位

P0 只读 → P1 改本仓库 → P2 预算内真实调用 → P3 授权范围内操作云平台。档位是 Skill 的行为约束；真正的隔离要靠运行环境（独立工作区、受限凭据），这在 [后续路线](roadmap.md) 中。

## 控制台

对话式的交付动作（回答问题、签字、照清单验收）对非技术用户来说麻烦且容易漏，所以加了本地控制台：

- **AI 和界面之间用“收件箱”交接。** AI 非交互运行，把问题、待办、验收清单、审批摘要写进 `factory/inbox/<阶段>.json`；界面把它们变成表单；用户的输入在下一次运行时交给 AI。这样任何能读写文件的 AI 助手都能接入（Claude Code、Codex 自动执行；其他助手通过复制指令接入）。
- **状态只归控制台。** AI 运行期间锁定状态写入，运行后比对 state.json，被改就恢复；证据和阻塞由控制台根据收件箱记录，并做等级上限检查。审批只来自界面操作。
- **“下一步”由规则算出，每屏只给一件事。** 优先级：AI 运行中 → 回答问题 → 本人操作 → 部署授权 → 照清单验收 → 修复 → 补齐缺口 → 签字 → 进入下一阶段。
- **技术选型偏离了默认技术栈。** 默认栈是 FastAPI + Next.js，但控制台是给非技术用户在本机运行的工具，零安装比框架便利更重要：后端只用 Python 标准库，前端是不需要构建的原生 JS 模块。

## 不包含

- 课程 s01–s17 的参考代码（体积大、属于课程材料）；蓝图 Skill 只保留机制索引并注明可对照参考实现。
- 产品模板仓库（预置登录、任务模型、存储抽象、日志、CI 的起步项目）；这是下一步最值得做的部分。
- 云端托管与多人协作（控制台目前只在本机运行，一个人使用）。
