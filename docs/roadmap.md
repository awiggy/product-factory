# 后续路线

按“先跑通一个真实产品，再自动化”的顺序推进。

## 第 1 步：试跑一个小产品（现在就能做）

- 选一个 1–2 周能做完的小产品，用 product-factory 从 PRD 走到上线。
- 每次卡住、AI 做错、文档不好用时，在本仓库记一条：哪个阶段、发生了什么、期望什么。
- 只根据真实问题修订 Skill，不为个例增加全局硬规则。

## 第 2 步：产品模板仓库（价值最大）

把每个产品都要重复写的部分做成一个起步仓库，AI 只写业务部分：

- 后端：FastAPI 项目结构、配置加载、统一错误结构、模型调用适配层（超时/重试/日志）、任务状态模型与持久化、SSE 约定、存储抽象（本地/对象存储可切换）、邀请码登录与按用户隔离、trace_id 日志。
- 前端：Next.js 骨架、API 客户端与错误归一化、12 个任务状态的映射与通用组件、流式处理。
- 工程：.env.example、.gitignore、CI（lint/类型/测试/构建）、mock 与真实冒烟两套测试入口、`factory/` 目录。
- 技术适配阶段改为：从模板创建 → 只写差异。

## 第 3 步：让流程自动跑起来

- 用 CI 在每次提交时运行 `factory_gate.py check` 和 `eval_cases.py`，在 PR 上显示闸门状态。
- 写一个调度脚本：读取 state.json，自动执行不需要审批的阶段（如 adaptation 无偏离时），到审批点发通知（邮件/飞书）后暂停。
- 每个产品在独立工作区或容器里运行；凭据按阶段档位发放（P2 只有测试模型 Key，P3 才有云凭据，且来自密钥管理）。

## 第 4 步：多产品看板

- 汇总所有产品仓库的 state.json：阶段、阻塞、待审批、证据等级、费用。
- 评测用例与结果跨版本对比，观察模型/Prompt 变更的效果。

## 待验证的假设

- 7 个阶段的划分是否合适（例如小产品是否应合并 blueprint 与 adaptation）。
- 证据等级要求是否过严或过松。
- 审批点数量是否让人疲劳。
