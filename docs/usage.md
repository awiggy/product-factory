# 使用说明

> 推荐用控制台：双击 `启动控制台.command`，所有交付动作都是界面操作，见 [控制台说明](../console/README.md)。下面是不用控制台、直接在对话里使用 Skill 的方式。

## 准备

- 安装：`./scripts/install.sh`（或把 `skills/` 下需要的目录复制到助手的 Skill 目录，保持目录内相对路径）。
- 一个产品一个 git 仓库。工厂记录放在仓库的 `factory/` 目录，和代码一起提交。
- 模型 Key 在需要真实冒烟时再填进项目的 `.env`（不提交），不要发到对话里。
- 云平台账号在上线阶段再准备。

## 一轮完整流程怎么说

下面是你在每个阶段对助手说的话，以及你需要做的事。助手每完成一个阶段都会停下来给你审批摘要。

| 阶段 | 你说 | 你要做的 |
| --- | --- | --- |
| 开始 | “使用 product-factory，为〈产品名〉建立工厂流程。我的想法是……” | 回答 PRD 访谈问题（每轮最多 3 个） |
| PRD | （助手写完后）“PRD 确认，进入下一步。” | 看一句话定位、范围、红线、AC 是否对 |
| 蓝图 | “继续。” → 审批时：“蓝图确认。” | 看是否引入了你不想要的费用、外部系统、自动化程度 |
| 技术适配 | “继续。” | 只有出现偏离默认方案或新增费用时才需要你确认 |
| MVP | “继续。”；需要时把模型 Key 填进 `.env` | 按“照着做”清单亲自操作，确认后说“MVP 验收通过” |
| 前端 | “继续。”；提供设计稿或参考产品（没有也行） | 看代表页给意见；按清单在浏览器/真机验收 |
| QA | “继续。” | 确认效果评测的阈值；参与人工评分 |
| 上线 | “准备上线到〈平台〉。” | 注册/实名/建子账号/在自己终端登录 CLI；审批 release_go（含费用与公开范围）；按上线清单验收 |
| 运营 | “整理这两周的反馈。” → “开始 v2，范围是……” | 决定下一版做什么 |

随时可以问：“现在到哪一步了？”助手会运行 `status` 回答。

## 单独使用某个 Skill

```text
使用 prd-author。我想做一个帮家长把旧玩具编成亲子剧本的小程序，先帮我把想法问清楚，写成 PRD。
```

```text
使用 agent-blueprint。根据附件 PRD，判断固定工作流还是 Agent 更合适，给出五要素、组件取舍、工具权限与验收计划。只做方案。
```

```text
使用 agent-mvp-delivery。基于现有项目和 PRD，先写技术适配声明，再实现第一阶段闭环；区分 mock 与真实模型验收。
```

```text
使用 qa-eval。根据 factory/prd.md 的验收标准写评测计划和用例，检查覆盖。
```

```text
使用 agent-release-readiness。只检查是否具备上线条件，不部署、不购买资源。
```

## 常见情况

| 情况 | 怎么办 |
| --- | --- |
| 还没有模型 Key | 开发照常用 mock 推进；到 MVP 验收时补 Key。确实拿不到时，你可以豁免（waive），报告里会标注 |
| 下游发现 PRD 有问题 | 助手会记录阻塞并建议回到 prd 阶段修订，重新签字后继续 |
| 不需要界面（纯 API） | 在前端阶段确认跳过并写明理由 |
| 已有项目，不是从零开始 | 照常从 PRD 开始（可以把现有文档交给 prd-author 完善）；技术适配阶段会沿用现有技术栈 |
| 只想做个演示，不正式上线 | 在 release 阶段说明“受限演示”，发布记录会写清数据可能丢失、访问范围受限 |
| 线上紧急修复 | 在当前版本记录阻塞，修复后过 QA 相关用例与发布检查重新发布，不必开新版本 |

## 签字的两种方式

- 在对话里明确说“批准”“确认”，助手会带上你的原话记录。
- 自己运行：`python3 factory_gate.py approve <仓库> --id <审批id> --by "<你的名字>" --quote "<你的话>"`

助手不会在同一轮里替你签字，也不会把“看起来没问题”当成批准。
