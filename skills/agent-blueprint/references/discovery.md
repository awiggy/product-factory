# 从点子到可推导需求

工厂流程中，完整的需求澄清由 prd-author 负责。这里是没有 PRD、用户又只要架构初版时的简化做法。

先阅读已有资料，不把已经回答的问题再问一遍。对不熟悉术语的用户，每轮只问少量高影响问题，并说明为什么要问。

## 三轮澄清（按需，不是强制访谈）

1. 用户与目标：给谁用、现在怎么解决、要得到什么结果。
2. 核心流程：输入从哪里来、结果交到哪里、涉及哪些外部系统和人工决定。
3. 风险与验收：哪些数据不能出域、哪些动作不能自动执行、失败如何恢复、怎么判断真的有用。

已有足够信息时直接提出初版方案。只把会改变架构、授权、费用或隐私的未知当作阻塞；其余明确写成可调整假设，不能当成用户已确认的事实。

## 事实记录

每项记录“内容、来源/用户原话、确定程度、影响的决策”。只保留与当前架构相关的内容，不复制整段会话。

需要明确：目标/不做什么、用户与访问方式、一次完整业务闭环、输入输出、系统依赖、数据保留与可见范围、允许的行动、失败兜底、可衡量的验收条件。

不要编造准确率、并发、成本或时延承诺。可以提出待测目标和测量方法，但标明尚未验证。

## 是否需要 Agent

- 输入输出固定、步骤稳定且规则明确：普通程序或工作流可能更合适。
- 模型只负责分类、抽取、生成：可以嵌入固定流程，不必开放自主工具循环。
- 需要按中间结果动态选择下一步：考虑有边界的 Agent。
- 部分步骤必须确定、部分需要探索：固定主流程搭配局部 Agent。

例：报销审批中的金额校验用确定性规则，票据字段抽取可用模型，付款必须走已授权的业务流程；不能为了“Agent 化”让模型随意决定权限和付款。

## 冲突处理

例如“文件不得出本机”与“全文发送给外部模型”同时出现时，指出冲突，提出本地模型、脱敏/最小化传输或调整授权等选项。不偷偷默认允许外传，也不擅自决定供应商。
