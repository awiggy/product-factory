# 技术适配：先看约束，再选默认方案

## 选择规则

| 情况 | 决策 |
| --- | --- |
| 已有可维护的技术栈 | 沿用；更换框架、语言或数据库必须有任务内理由与迁移方案 |
| 全新项目，无团队偏好与平台约束 | 直接采用 [默认技术栈](default-stack.md)，不做开放式选型；创建时确认当前受支持版本并锁定 |
| 已有 Node、Java、Go 服务 | 不为模板偏好增加第二种后端语言 |
| 单机低并发 MVP | SQLite 可以是选项；部署到临时文件系统、多实例或高并发时重新评估 |
| 人工批准决定 Agent 能否继续 | 一开始做可确认、可拒绝的最小 UI 与后端闭环 |
| 静态演示，无真实任务 | 明确演示标签，不添加假 API 在线状态，不宣称真实业务通过 |

鉴权、任务队列、向量库、消息系统、多租户、支付、语音均由需求触发，不能因为“AI 产品”就全部安装。也不能把必须保护真实数据的鉴权推迟为装饰性后续项。

## 最小适配声明

- 目标用户与这次闭环。
- 已有项目证据：依赖、接口、测试、部署形态。
- 保留什么；新增什么及原因；不做什么。
- 数据归属、身份边界、模型提供方和外部副作用。
- 测试如何判定成功；哪些条件缺失会标记未验证。
- 仅列需要用户决定的关键分歧。

小改动可在回复中写清，不强制生成长篇设计。新产品或跨模块变更才补阶段记录；使用项目现有结构。
