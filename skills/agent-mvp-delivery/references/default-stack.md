# 默认技术栈与工程底线

适用于从零开始、没有既有系统约束的 Agent MVP。规则分三层：

| 层 | 含义 | 处理 |
| --- | --- | --- |
| A 强制底线 | 与安全、数据、可恢复、可验证直接相关 | 必须遵守；公司或法规更严时用更严的 |
| B 默认方案 | 适合大多数新 MVP | 直接采用；触发适配条件时给一个替代方案并说明理由 |
| C 按需模块 | 特定需求出现才有价值 | 由 PRD/AC 触发才引入，不为“完整”预装 |

判断顺序：先查强制底线 → 再看默认方案是否适配 → 最后只引入被需求触发的模块。

## 默认组合（B）

| 层 | 默认 | 说明 |
| --- | --- | --- |
| 后端 | Python 3.11+、FastAPI、Pydantic、pytest | 创建项目时确认当前受支持版本并锁定 |
| 模型调用 | 官方 SDK 或经过验证的兼容接口，经适配层调用 | 模型名、base_url、超时、参数走配置 |
| Web 前端 | Next.js（App Router）+ TypeScript strict + Tailwind，Node 当前 LTS，npm | 详见 agent-frontend-delivery |
| API 前缀 | 公开 API 用 `/api/v1`；内部 MVP 可用 `/api` 但集中定义 | 已有项目保留现有前缀 |
| 编排 | 固定业务流程用代码状态机；只有确需动态选工具时才开放有边界的 Agent 循环 | |
| 代码管理 | Git（A 层） | 新项目初始化并配置 .gitignore |

## 按需模块（C）

| 触发条件 | 默认模块 | 不该引入的情况 |
| --- | --- | --- |
| 多实体关系、事务、账户、并发修改 | SQLite + SQLAlchemy + Alembic；上线前评估 PostgreSQL | 单用户本地、资产文件为主时可先用带 schema 版本的文件清单 |
| 语义检索 / 知识库问答 | Chroma 持久化模式；上线评估 pgvector 等 | 没有 RAG，或全文搜索够用 |
| 读写 Word | python-docx（只支持 .docx） | 无此需求 |
| 文本 PDF | pypdf | 扫描件需求才引入 OCR |
| 长耗时、并发任务 | 持久化任务记录；达到规模再上任务队列 | 短请求 |
| 大图片/音视频/生成文件 | 本地目录；上线用对象存储 | 不塞进关系库 |
| 逐步展示模型输出 | SSE；或“提交 + 轮询状态 + 取结果” | 只需最终结果时 |

## 默认目录（新建后端先行项目）

```text
project/
├── backend/
│   ├── app/
│   │   ├── api/          # 路由
│   │   ├── core/         # 配置、安全、日志
│   │   ├── models/       # 数据库模型（使用数据库时）
│   │   ├── schemas/      # 输入输出结构
│   │   ├── services/     # 业务、模型、Agent、RAG
│   │   │   └── prompts/  # Prompt 独立文件
│   │   ├── static/       # 一次性验收页面（需要时）
│   │   └── main.py
│   ├── tests/
│   └── requirements.txt  # 或 pyproject + 锁文件，二选一
├── frontend/             # 选择 Web 或纵向切片时
├── factory/              # 工厂决策与证据
├── .env.example
├── .gitignore
└── README.md
```

不需要的目录不创建空壳；已有项目延续现有结构。

## 强制底线（A）摘要

**API 与任务**
- 每个 API 定义请求、响应和错误结构；错误统一格式，不向用户暴露堆栈。
- 前端只经受控 API 访问后端，不直连数据库或密钥存储。
- 长任务持久化可恢复状态，不依赖内存变量，不让一次 HTTP 请求无限等待。

**数据**
- 重要数据与任务状态在进程重启后可恢复。用结构化文件时须有 schema 版本、原子写入、损坏处理和并发边界。
- 状态用明确枚举，新增状态考虑旧数据兼容；删除重要数据前确认，生产优先软删除。
- 本地文件通过结构化存储登记归属、路径、状态，不靠目录猜关系。

**模型与 Agent**
- Prompt 独立管理、可追溯版本。
- 模型调用处理超时、失败和有限重试，包括 SDK 初始化失败（例如没有 Key 时在构造客户端阶段就会抛错，要在调用链最外层兜底）。
- 结构化输出：模型按标准格式输出 → 后端确定性解析 → Pydantic 强校验 → 有限重试 → 统一错误。格式约束三件套：
  1. Prompt 给正例，并写明禁止的反例。
  2. 解析器兼容常见等价格式，不只认一种然后靠重试硬扛。
  3. 数量/内容约束没遵守（如要求 3–5 条给了 8 条）记为质量瑕疵交用户判断，不当解析错误反复重试烧钱。
- 记录模型、耗时、token 和错误类型，不记录密钥与敏感原文。
- 高风险、不可逆、对外发送或涉及费用的动作，由确定性代码和权限策略控制，不交给模型决定。
- 关键人工确认点持久化，刷新、重启、换终端后可继续。

**配置与安全**
- 密钥只在后端可读、不进仓库的载体：本地 `.env`（加入 .gitignore，只提交 `.env.example`），线上用平台密钥管理。
- 模型 Key 不进前端代码或构建产物；允许用户录入 Key 时，只提交到受保护后端，响应脱敏，日志不记录。
- 上传文件检查格式、真实内容类型、大小与安全文件名，防路径穿越。

## SSE 事件约定（使用 SSE 时）

- 事件序列：`chunk` 零到多次，最后必为 `done`（含完整结果）或 `error` 之一。
- 中途失败用 `error` 事件返回与普通响应相同的错误结构 `{"error": {"code", "message"}}`；不静默断流，不把堆栈写进流。
- 冒烟方法：`curl -N` 调用并计时，确认首个 chunk 时间、收尾事件与错误结构。

## 双层验收

| 层 | 何时 | 内容 |
| --- | --- | --- |
| mock 自动化 | 每次开发完成必跑 | 业务逻辑、状态迁移、参数校验、错误路径、解析器单测；离线可跑 |
| 真实模型冒烟 | 阶段验收前必做 | 认证与 SDK 初始化（无 Key/错 Key）、真实超时与限流、输出质量（首测合规率与重试后合规率分开记录）、真实延迟 |

最低要求：每种模型调用契约、每条关键用户链路，至少一条“真实输入 → 真实模型 → 持久化/返回 → 用户可查看”的完整路径，并记录模型、时间、成本和结果。多个接口复用同一已验证模型服务时，不必机械重复付费调用，但要写清覆盖关系。

不能通过删除测试、隐藏报错、用 mock 冒充真实验证或降低标准来宣称完成。

## 本地方案与上线方案

| 能力 | MVP | 上线（由 release 阶段评估） |
| --- | --- | --- |
| 结构化数据 | SQLite 或带 schema 的文件 | 按并发与查询需求用托管 PostgreSQL 等；单实例 SQLite 仅在持久卷 + 一致性备份确认后可用 |
| 向量检索 | 本地 Chroma | pgvector 或托管向量服务 |
| 文件 | 本地目录 | 对象存储（私有桶 + 鉴权下载） |
| 后台任务 | 进程内执行 + 持久化状态 | 达到阈值后用任务队列 |
| 登录 | 暂不实现或基础登录 | 邀请码 / OAuth / SSO，按 PRD |
| 监控 | 本地日志 | 结构化日志 + trace_id + 错误告警 |

从 MVP 升级到上线方案前，先输出迁移方案（数据迁移、配置变化、兼容风险、回滚方式）再改代码。
