# 数据可靠性与回滚

## 上线前画清数据去向

列出数据库、上传文件、生成产物、任务状态、缓存和日志各自的位置、所有者、保留策略与恢复方法。区分可丢弃缓存和业务事实源。

不要把 `/tmp`、容器可写层或未确认持久语义的本地路径当唯一存储。实例保活只影响运行策略，不证明磁盘耐久性；多副本不自动带来一致性。

SQLite 并非一律不能上线，但需要确认持久卷、单写/并发边界、锁行为及一致性备份方式。数据库运行中不能仅复制主文件就宣称备份完整，尤其启用 WAL 时。多实例读写需要适合该拓扑的数据库方案，不能靠定时覆盖同一对象解决。

## 备份和恢复

先确定可容忍丢失多久的数据（RPO）与恢复多久可接受（RTO）。备份频率并不直接证明这些目标已达到。

记录备份对象、快照一致性、加密与访问权限、保留策略、恢复步骤和验证方式。在获授权的隔离环境恢复样本，检查记录、文件关联与核心查询；无法演练时明确“恢复未验证”。不向生产直接覆盖恢复。

对象存储适合文件产物，但不是数据库事务替代品。核验私有桶/访问策略、对象归属、下载鉴权或短期签名；不因分享文件而将整个桶公开。

## 分开看三种回滚

- 代码：上一个可部署版本与配置兼容性。
- 数据结构：优先向后兼容迁移；破坏性迁移需要备份、范围确认与独立恢复/前向修复方案。
- 业务副作用：已发送消息、已付款或调用外部工具不能通过代码回滚撤回，需单独补偿。

发布前写明触发条件（如关键接口持续失败、权限回归、数据写入异常）、观察窗口、负责人及执行方式。阈值按项目目标确定，不虚构统一数字。未经测试的回滚仅叫预案，不叫“已验证可回滚”。
