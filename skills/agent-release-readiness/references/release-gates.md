# 发布门槛

根据用户范围检查，不把企业级功能清单强加给小型静态演示；涉及真实账户、文件、模型费用时不能略过相应保护。

| 门槛 | 最小证据 | 常见误判 |
| --- | --- | --- |
| 版本与构建 | 指定 commit、实际构建产物/部署版本、入口与运行依赖 | 首页显示正常但仍是旧版本 |
| 访问控制 | 登录及至少两个测试身份的数据隔离；文件/任务接口同样检查 | 隐藏前端按钮当作权限 |
| 配置与密钥 | 必要配置名称齐全、服务端注入、日志脱敏 | 把密钥写入前端 bundle 或 README |
| 数据与文件 | 持久存储位置、重启后读取、备份与恢复证据 | 把临时磁盘或实例保活当永久存储 |
| 核心业务 | 已授权测试账户完成一条真实输入到结果/历史的流程 | health/200 代替业务验收 |
| Agent 边界 | 超时、重试、工具范围、调用/费用上限、确认机制 | 无界自动重试供应商请求 |
| 故障与观测 | 可定位请求/任务 ID、用户可见错误、告警或人工巡检安排 | 出错只显示无限加载 |
| 发布恢复 | 上一稳定版本、数据库兼容策略、回滚触发条件 | 代码回滚等于数据库恢复 |

发布前记录阻塞与未验证项。针对含真实数据或费用的公开生产服务，权限隔离或持久化未验证属于阻塞。用户仅需要受限 demo 时，明确隔离演示数据与访问范围，不伪称生产就绪。

发布后核对实际版本，验证浏览器访问、API、权限、关键数据读写、历史恢复与必要的外部依赖。测试写入使用明确的测试数据，不向真实用户发消息或执行真实付款。测试残留按既定方案清理，不宽泛删除。

结果按“发布成功且已验证”“部署存在但业务未通过”“未部署/被阻塞”分别报告；附观察时间、环境与证据，不把三个状态混称上线成功。
