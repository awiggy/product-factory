# PRD 质量检查

交给用户签字前逐项检查。不满足的项要么补上，要么写进“待确认”并说明影响。

## 必须项

- [ ] 一句话定位包含用户、痛点、结果。
- [ ] 核心闭环写成“角色 → 输入 → 过程（含用户确认点）→ 产物 → 保存/再次查看”。
- [ ] MVP 范围、后续版本、明确不做三栏分开。
- [ ] 每个外部依赖（模型、API、数据源）写了用途和是否已有账号/授权。
- [ ] 红线至少覆盖数据隐私、不可逆操作、内容安全。
- [ ] 失败与降级覆盖：输入不合法、模型超时/失败、输出不合格、外部依赖不可用。
- [ ] 每条 AC 有编号，可由一个不了解背景的人照着验证。
- [ ] 成功指标有目标值，或标明“待测目标 + 测量方法 + 谁来定”。
- [ ] 待确认项写清影响哪个决定、谁来回答。

## 验收标准（AC）写法

格式：`AC-n｜场景｜给定条件｜操作｜预期结果｜判定方式`

好的例子：
- AC-3｜上传扫描版 PDF｜文件无可复制文字｜上传｜提示“暂不支持扫描件”，可改为粘贴文本，原输入不丢失｜手工 + 自动化
- AC-6｜术语解释质量｜20 篇 AI 领域论文抽样｜生成术语卡片｜人工抽检 100 条，明显错误 ≤ 5 条｜人工评测，阈值待产品负责人确认

不好的例子：
- “翻译要准确”（无法判定）
- “系统稳定”（无场景、无指标）
- “支持所有文件格式”（范围无边界）

Agent 效果类 AC 必须写：评测样本从哪来、多少条、谁判定、可接受的瑕疵（例如格式小错算瑕疵不算失败）。

## 常见问题

| 问题 | 处理 |
| --- | --- |
| 写了技术方案（“用 Redis 缓存”） | 移到约束（若是硬要求）或删掉，交给后续阶段 |
| 功能清单很长但没有闭环 | 先写一条完整闭环，其余放后续版本 |
| 指标是编的 | 改为待测目标，注明来源缺失 |
| 红线只写“注意安全” | 写成具体禁止行为与处理方式 |
| 把多个产品塞进一个 PRD | 拆分，或明确 v1 只做其中一个 |
