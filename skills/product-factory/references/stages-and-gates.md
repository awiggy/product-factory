# 阶段与闸门

## 闸门由四部分组成

`factory_gate.py check` 对当前阶段逐项检查，全部满足才可 `advance`：

1. **交接物**：stages.json 列出的文件存在、非空，Markdown 文件不含模板标记 `<!-- factory:template -->`。各阶段 Skill 从自己的模板起稿时保留这行标记，写完后删除。
2. **阻塞清零**：`blockers` 为空；失败证据须已处理（修复后追加一条 pass 证据，并在原条目标 `resolved`，或由用户豁免）。
3. **证据等级**：已通过证据中的最高等级 ≥ 该阶段 `min_evidence`。条件不具备（例如还没有模型 Key）时，只能由用户 `waive --item min_evidence`，报告里会显示为豁免。
4. **用户审批**：`mode: required` 的审批必须有记录；`conditional` 的先由 AI 用 `set --approval-required` 声明是否需要。

## 证据等级（从低到高）

| 等级 | 含义 | 不能证明 |
| --- | --- | --- |
| planned | 文档或方案已写 | 任何东西能运行 |
| scaffold_runs | 骨架能启动 | 业务正确 |
| mock_passed | 离线自动化测试通过 | 真实模型可用、效果达标、计费正确 |
| real_passed | 已授权的真实模型/第三方冒烟通过 | 全部场景、长期稳定、线上环境 |
| production_verified | 目标环境中版本、核心业务、权限、持久数据经实际验证 | 未覆盖的安全与可靠性 |

用户验收不是证据等级，而是审批（build_acceptance 等）。

## 各阶段的闸门要点

| 阶段 | 额外关注 |
| --- | --- |
| prd | 验收标准带编号（AC-n）且可测；待确认项中没有会改变架构、费用或隐私的未决问题，或已经被用户接受为假设 |
| blueprint | 每个选中组件有需求依据；工具都有权限与副作用说明；有预算/步数/停止条件 |
| adaptation | 技术适配声明第 6 节“需要用户决定的问题”为“无”时，可声明 approval_required=false |
| build | 双层验收：mock 自动化 + 真实模型冒烟；每条关键链路至少一条真实路径 |
| frontend | lint / typecheck / test / build 通过，并有真实浏览器验收，不能只看构建成功 |
| qa | 每条 AC 都有对应用例与结果；效果评测有指标和样本量；阻塞缺陷为 0 |
| release | 部署前 `require --id release_go`；结束时有版本核对、真实业务、权限隔离、持久化与恢复证据 |

## 权限档位

| 档位 | 允许 | 不允许 |
| --- | --- | --- |
| P0 只读 | 读资料与代码；写 factory/ 下文档 | 改代码、调用付费模型、触达外部系统 |
| P1 工作区写 | 改本产品仓库、跑本地测试 | 付费服务、云资源 |
| P2 真实冒烟 | P1 + 预算内调用已授权的真实模型/测试接口 | 云资源、真实用户消息、真实付款 |
| P3 发布 | P2 + 在 release_go 授权范围内操作云平台 | 超出授权范围的计费、删库、公开私有资源 |

执行端的权限优先于提示词：只读阶段若运行在有写权限的环境里，仍然只写 factory/ 文档，并在交接中说明。

## 回退

下游发现上游问题时，不改写上游结论：

- 记录阻塞，说明发现了什么、影响哪个决定。
- 需求问题回到 prd，架构问题回到 blueprint，修订后重新取得对应审批。
- 回退方式：用户确认后，把相应阶段与其后阶段的 `status` 改回 `in_progress` / `not_started`，并在 notes 写明原因（这是唯一允许手改 state.json 的情况，改完运行 status 校验结构）。
