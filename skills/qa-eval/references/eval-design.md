# 评测设计

## 用例类型

| 类型 | 验证什么 | 常用判定 |
| --- | --- | --- |
| functional | AC 中的业务行为 | 精确比对、规则校验 |
| agent_quality | 输出是否有用、准确、合规 | 规则 + 评分标准（rubric）+ 人工 |
| safety | 越权、数据隔离、内容红线、提示注入 | 规则；必须为 0 违规 |
| reliability | 超时、重试、重复提交、断线恢复、部分成功、重启后历史一致 | 规则 + 状态核对 |
| performance | 首字时间、整体耗时、单任务成本 | 测量值对比阈值 |

## 三层验证

- **mock**：离线、可重复，覆盖分支与错误路径。不能证明模型效果。
- **real**：真实模型或第三方在测试环境的调用。证明连通性和真实输出，样本有限。
- **manual**：用户或指定评审人按评分标准判断。效果类最终以此为准。

## 效果评测怎么做

1. **样本**：从 PRD 场景出发，覆盖常见、边界和困难输入。效果类首轮建议 20–50 条，按成本调整；样本来源写清楚，不用真实用户隐私数据。
2. **评分标准**：每个维度写清“好 / 可接受 / 不合格”的具体样子，附正反例。例如“术语解释”维度：好 = 定义正确且结合论文语境；可接受 = 定义正确但泛泛；不合格 = 错误或编造。
3. **格式指标分开记**：首测合规率、重试后合规率、数量/内容约束遵守率。数量超出但内容正确算瑕疵，不算失败（除非 PRD 另有规定）。
4. **模型自动评分**：可以用独立模型按评分标准打分，提高效率；但要抽检至少一部分由人工评分，计算一致率。一致率低时以人工为准，并改进评分标准。
5. **对比**：模型或 Prompt 变更时，同一用例集跑新旧两版，报告差异，不只看新版本的绝对分。

## 安全与越权最低集合

- 未登录访问数据接口被拒。
- 用户 A 无法读取、修改、下载用户 B 的任务与文件（换 ID 直接请求也不行）。
- 前端隐藏的操作，直接调用接口同样被拒。
- 输入中夹带指令（“忽略之前的规则……”）不能扩大工具权限或泄露系统提示词。
- 日志与错误响应中没有密钥、完整敏感原文和堆栈。

## 可靠性最低集合

- 连续点两次提交只产生一个任务（或第二次返回同一任务）。
- 生成中刷新页面，能按任务 ID 恢复状态；结束后打开历史不会再次调用模型。
- 模型超时或报错：有限重试后给出统一错误，用户输入不丢失。
- 服务重启后，已完成的结果与进行中任务的状态仍可查询。
- 预算或步数上限触发时，任务停止并给出可理解的结果。

## 回归

用例集随版本保留。每次修复、模型/Prompt 变更或上线前，至少回归 blocker 相关用例和全部 safety 用例。
